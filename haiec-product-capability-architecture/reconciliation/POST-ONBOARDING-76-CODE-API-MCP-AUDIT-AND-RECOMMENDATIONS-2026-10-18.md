## 3. Priority finding: P11.1 report consistency is P1 and NOT yet resolved in this audit

**P11 shipped** in HAIEC #2260 / frozen SHA. Public valid \`INTEGRITY_VERIFIED_AGAINST_HAIEC_RECORD\` vs \`INVALID_PACKAGE\` mapping is corrected using the shared display projection; source has been inspected. Reports Hub is evaluation-first; NO_RECEIPT is honest if derived exhaustively. P11 public UI source status is production-ready *according to existing independent handoff*, but **real public/verifier tenant cases remain separately NOT_RUN**.

Two additional P11.1 consistency issues are **source-confirmed in the ongoing canonical handoff**:
1. **False negative for older issued receipts** — \`app/api/inventory/systems/[id]/reports/route.ts\` uses \`findMany(orderBy createdAt desc, take:20)\` for system package list. \`app/dashboard/assurance/evaluations/[evaluationId]/page.tsx\` takes that bounded list and \`.find(assuranceEvaluationId===evaluationId)\`; no match becomes \`none\`. For a real evaluation with a package outside the newest 20 system packages, this can falsely show "No Decision Receipt recorded". **Correct reuse owner exists:** \`lib/ai-inventory/system-receipt-projection.ts::resolveEvaluationReceipt(evaluationId,aiSystemId,organizationId)\`, which does exact tenant+system+evaluation binding and representative selection. Require negative >20 packages / no receipt / wrong-tenant tests; don't break list pagination. A code-confirmed risk, NOT a reproduced customer incident.
2. **MCP vs UI representative difference** — \`haiec_get_package(evaluationId)\` can choose newest by \`createdAt\` whereas canonical representative receipt selection prioritizes PUBLIC > PRIVATE > REVOKED (then recency within state). Agents and UI can therefore disagree about the "default receipt" if multiple packages exist for the same evaluation. Preserve explicit packageId lookup while reconciling the exact evaluation selection and labeling. Reuse canonical selector, do not create new U6 verifier/receipt store.
These were already raised by [P11.1 MCP/agent-readable report handoff](../UX-P11.1-MCP-AGENT-REPORT-EXPLANATIONS-AND-ARTIFACT-PARITY-2026-10-18.md); this work adds them to the **76-ID audit priority** (I01/I02/I08) instead of launching a competing P11 task.

**Next active implementation:** P11.1 exact receipt read truth and deterministic **agent-readable Report Explanation Packet**, then P12 provider usage, then P13 UX shell (per latest Common Repo handoff). Model/agent interpretations must cite canonical evidence and never substitute for signed receipt/source truth. No standalone report product or generic auto-generated reasoning verdict.

## 7. ISAF v1/v2, CSM6 and LLMVerify crosswalk

- ISAF v1: research lineage and nine-layer/127-checkpoint inventory (not 127 executed customer tests); only selected *applicable and evidence-backed* checkpoint results map into a report appendix.
- ISAF v2: October 9 author-issued, **not peer reviewed**, bounded DCD reference qualification and hardened evaluator tests; held-out external validation NOT_RUN. Five independent evidence planes + orthogonal delegation, missing evidence means unresolved, source/hash/observed-effect distinctions. ISAF does not supersede U5 implementation evidence.
- CSM6: AI Governance Execution Framework six ongoing operating functions F1 purpose/accountability, F2 system/data/dependencies, F3 risk/evaluation/monitoring, F4 controlled delivery/change, F5 human oversight/feedback, F6 compliance/evidence/assurance. Application source \`lib/ai-security/csm6-mapping.ts\` says a scanner contributes selected technical evidence, not whole F1/F5 governance. Historical references to a specialized LLMVerify 38-rule CSM6-mapped pack cannot be used as proof that all six functions are implemented.
- Optional mapping in customer report: *relevant research/guidance*, version/citation, applicability, independent source/test qualification and remaining unknown. No automatic ISAF certification, full CSM6 operational certification or legal compliance badge.

## 9. Safety and evidence limitations
Source read is limited to exact commit and selected key routes; 60 MCP registered names are parsed from code rather than independently exercised by an authenticated client. This audit did not enumerate every HTTP route exhaustively, execute permissioned tenant tests, simulate all 76 workflows or prove production native target integration. The 14 exact REST row matches/73 existing page-family matches should be treated as a **floor of directly examined relevant anchors, not an exhaustive ceiling**. The source linked register is safer for marketing than optimistic complete matrices, but final customer availability needs targeted acceptance above.

**Bottom line:** The HAIEC engine does not need 76 new features. It needs transparent product/producer qualification; authoritative report/receipt join consistency; focused scoped enterprise integration where clients actually need added sources, ongoing response or true in-path enforcement.
