## 1. Decision

**Retain the existing strong Enterprise POC proposition, but compress educational catalog content and demonstrate the buyer outcome much earlier.** This is an editorial and conversion upgrade, not a rebrand, expanded feature claim, or another product engine.

**Page ownership:** Platform explains the six independent jobs; Products distinguishes the platform from independent tools; Assurance explains qualified evidence and deterministic assessment; **Enterprise sells one bounded evaluation of a consequential system and a decision**; /enterprise/architecture is already the 12-view technical deep dive; /pricing owns self-service tier facts and /docs/agent-integration owns MCP connection.

**Canonical company/category/tagline:** HAIEC — Human AI Evidence Company / Evidence-Bound Assurance / High assurance in every consequence. Technical descriptor: **Deterministic AI Action Assurance**. Do not replace brand/category with generic compliance software.

**Hero H1 — PRESERVE:** “Can you prove what this AI can actually cause?”

**Value proposition:** Qualified technical findings, consequential action/authority mapping, proof gaps, and technical/executive decision outputs bounded by actual source, controls, scope and testing authority.

**Buyers:** CISO/AppSec (approve risky agent), CTO/AI Platform (what code can reach vs intended limits), Governance/Assurance (technical support for a human decision), Procurement/Third Party Risk (more than a vendor questionnaire). The initial commercial wedge is one consequential AI system and one priority question, NOT a platform maximum.

## 4. Enterprise page — publishable headline/copy storyboard

### E0 HERO — Outcome first
**Eyebrow:** ENTERPRISE EVIDENCE-BOUND ASSURANCE

**H1:** Can you prove what this AI can actually cause?

**Subhead proposal:** Your AI agent may have the right tools and credentials — and still make a business decision nobody meant to delegate. HAIEC evaluates supported action paths, policy and authority evidence, code capability and observed facts, so your team can see what is established, what remains uncertain and what to decide before production or expansion.

**Micro proof line:** Deterministic AI Action Assurance · Explicit evidence boundaries · Accountable decisions

**Primary CTA:** Scope My Enterprise POC → #qualify. **Secondary CTA:** See a Decision Example → #decision-example. Supporting: See What the POC Produces → #outputs.

**Qualifier in plain sight:** One consequential system / one priority question / minimum sufficient evidence / typical $25K–$75K scoped engagement; commonly 4–8 weeks after readiness; final scope/timing/deliverables by SOW.

**Hero visual:** A compact “decision dossier” for one synthetic support agent and refund API — code path supported in the fictional case, delegated recipient choice UNKNOWN. It must say **ILLUSTRATIVE, NOT LIVE ASSURANCE**. Do not paste the full 12-view architecture diagram in a narrow hero.

### E1 THE PUZZLE — Curiosity-led
**H2:** Permission to call an API is not permission to make every decision.

**Copy:** A support agent can pass a security scan, hold a valid credential and call an approved API. Yet the evidence may never establish that anyone authorized it to choose a refund recipient. A scanner, IAM, policy and runtime traces answer different questions. HAIEC compares those facts without quietly turning a missing authorization into a green result.

**Four manually selected visual beats:** Code can call refund API → the credential may grant action → delegated recipient choice remains UNKNOWN → human must review what the evidence supports. This is teaching, not an executed test. The five evidence planes remain peer lenses, never a sequential progression. DAI delegation is not a sixth plane.

### E2 WHAT ENTERPRISE RECEIVES — Decision specimen
**H2:** From technical facts to an executive decision.

**Copy:** Instead of another score, receive a scoped technical baseline, an evidence frontier, relevant security/authority findings, and a decision readout that separates established facts from unresolved questions.

**Illustrative specimen fields:** System and exact scope; supported agent/tool/API path; relevant policy and grant evidence; delegation gap; observed NOT_ASSESSED unless a real trace is provided; source coverage; illustrative REVIEW evaluation; next qualified evidence needed; human decision possibilities. Label **SYNTHETIC TEACHING EXAMPLE** in headline and caption.

**DO NOT CONFLATE:** HAIEC's scoped canonical ALLOW / REVIEW / BLOCK evaluation with POC executive recommendations Proceed to Pilot / Remediate & Retest / Evidence Upgrade / Stop or No Expansion; neither implies target-native block or approval receipt installed at the customer's gateway.

**True proof links:** /sample-reports, /sample-ai-action-access-map, /enterprise/architecture. Manufacturing/TMF demos are only shown with conspicuous synthetic/evidence-reference labels. No invented customer endorsement.

### E3 WHEN TO BUY
**H2:** Make the decision before the AI changes your business.

Three buyer moments: (1) approve consequential agent or new permission, (2) answer security/procurement and customer assurance review, (3) investigate change/near miss/unknown high-impact access. Existing nine triggers and buyer personas stay in searchable semantic disclosure, not hero chips.

### E4 SCOPE AND ACCESS
**H2:** Start focused. Expand only when the evidence requires it.

**Copy:** Establish the system owner, the consequential choice, source/environment boundary and the minimum authorized access necessary. Deep evidence may require IAM/configuration, controlled test or optional production signals. No telemetry or production execution should be implied by a source-only POC.

L0 documents & declaration; L1 source & implementation; L2 controls & authority; L3 controlled behavioral checks; L4 production-relevant read-only data. Make levels selectable to **explain** evidence strength, not imply sequential gates or automatically purchased scope.

### E5 HOW POC WORKS
**H2:** A controlled evaluation, not an open-ended audit.

Editorial groups: Define & authorize / Discover & map / Validate & qualify evidence / Review the decision. Preserve the existing seven specific steps inside accessible details; these commercial engagement activities are not HAIEC's six standalone platform jobs.

### E6 DELIVERABLES — group the existing 12 without deleting them
**H2:** Four decision-ready work products, scoped to the question.

| Outcome family | Current possible deliverables to retain | Executive value |
|---|---|---|
| System & Action Baseline | AI System Baseline; System Constellation; Agent Reachability; Shared-Substrate / Potential Influence | Which actions/resources are supported within coverage? |
| Assurance & Control Findings | Evidence Coverage / Frontier; Security/Control Findings; Authority & Capability Divergence; Evaluation-Integrity Exposure | What does the qualified technical proof say? |
| Limits & Next Actions | Unknowns & Limitations Register; Decision Receipt where supported; Prioritized Validation Backlog | What is unresolved, and who needs to do what? |
| Executive Decision Readout | Executive Decision Readout | What should the accountable human committee do next? |

The full list is **potential contracted outputs**, not twelve guaranteed deliverables or twelve separately sold modules. No package/receipt promised without actual qualification and entitlement.

### E7 COMMERCIAL CLARITY
**H2:** A defined scope, decision and evaluation window.

**Copy:** Typical scoped POC range $25K–$75K. Initial evaluations commonly take 4–8 weeks **after readiness**. The statement of work defines actual scope, access, data boundaries, tests, responsibilities and deliverables. More systems or customer-native protections require separately scoped expansion.

Use the existing overlap-aware timeline (pre-day1 / week1 / weeks1–3 / weeks2–5 / weeks3–7 / weeks4–8). Never turn it into fixed promises or artificial $25K/$45K/$75K tier cards.

### E8 TRUST AND DATA BOUNDARIES
**H2:** Evaluate sensitive AI without assuming blanket access.

**Copy:** Minimum sufficient access, named identities and targets, nonproduction first where feasible, customer-approved data handling, authorization before active tests, and explicit source/evidence gaps. **Local/offline Docker deployment must be technically and contractually qualified; do not promise fully local or zero egress until demonstrated with a tested install and representative dependencies.** Keep the Trust/Security link and document data retention in actual engagement.

### E9 OPTIONAL ENTERPRISE EXPANSION — not separate SKUs
**H2:** Expand from an evidence-backed baseline, where deeper work changes the outcome.

Do not sell generic “all six services.” If useful, one modest expandable section covering:
- Deeper independent validation and qualified evidence sources (prior proposed F1, relevant F5).
- Connected operations, monitoring and enterprise IAM/change workflows (F2/F4, selective F6).
- Customer-native action safeguards, recovery and effect verification only with real target integration (F3).

These are **potential scoped services** and buyer outcomes, not six published plans, required upgrades or proof of generic installed enforcement. Existing common plan [six grouped families](POST-ONBOARDING-CORE-VS-EXTENSIONS-COMMERCIAL-AND-TEMPLATE-PLAN-2026-10-18.md) remains the internal grouping owner.

### E10 FORM
**H2:** Tell us the decision you need to defend.

**Copy:** Share the consequential AI system and the question that needs a technical answer. We review fit and the evidence boundary before proposing an engagement. Sending an inquiry does not grant testing access or authorize use of your data.

Step 1 existing required fields: name, work email, company, role, assurance question/system summary. Step 2 existing optional qualifiers: type, evidence, timing, procurement, budget, partner and framework, with required CAPTCHA. Wording should be “Optional context and verification,” not a skippable step. Repair stable id/htmlFor, autocomplete, error descriptions, keyboard focus and success confirmation; preserve existing /api/contact contract and conversion tracking. If changing button to “Request POC Scoping,” ensure no implied commitment to buy.

Sample placeholders: “Can this support agent change refund recipients?”; “Could the MCP tool reach another tenant?”; “What becomes reachable with a new agent permission?”

### E11 MCP SECONDARY ENTRY, not primary sales funnel
**H3:** Want to inspect your own agent first?

**Copy:** Connect HAIEC's authenticated MCP server to a compatible AI assistant, then say **Run HAIEC AI Assurance**. HAIEC checks readiness and eligible evidence before an authorized run; the assistant guides the process and never assigns the canonical evaluation.

URL: https://www.haiec.com/api/mcp. Setup link: /docs/agent-integration. Operational playbook: /developers/mcp-playbook. No key in chat text, URL, source code or public JS. Preflight before run, eligible org/system/source/scope/consent and explicit approval for writes/tests. Do not imply any assistant can configure MCP solely from a message.

### E12 FINAL CTA / QUESTIONS
**H2:** Before the next consequential AI decision, establish what the evidence supports.
Primary Scope My Enterprise POC → #qualify; secondary See a sample report → /sample-reports.

Visible questions: What exactly is evaluated? Is production access required? Can source-only review start? What if evidence is incomplete? Is this a subscription? Can we deploy fully locally? How is this different from a third-party certification? Can an agent operate HAIEC? Answer within actual contracts; no unverified FAQPage rich-result promise.
