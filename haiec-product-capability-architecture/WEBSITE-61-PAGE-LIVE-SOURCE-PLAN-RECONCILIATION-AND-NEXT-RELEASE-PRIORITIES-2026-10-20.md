## P0 | Claim and trust sources that should govern the next release
1. **Trust, Privacy, retention and pricing facts.** Current /trust says audit logs are retained seven years, /privacy specifies default 90-day audit retention, and /pricing has tier-specific 30/90/unlimited scan history. They MAY represent different record classes, so enumerate the actual tables, jobs, entitlement gates and legal policy owner before changing copy. Publish a consistent scope- and data-class-specific retention matrix. Do not arbitrarily choose a number.
2. **Customer data/source and website analytics.** Trust presents broad assertions that no source content, production data or raw PII is retained. Validate the actual repository scan, GitHub remote source, uploaded evidence, provider connections, runtime response excerpts, report attachments, analytics and RB2B/Retention.com visitor identification. /privacy acknowledges RB2B/cookie behavior. Distinguish the default scan from optional evidence and configured connections. Do not make blanket no-PII guarantees.
3. **Certifications and operating security.** Verify provider SOC 2 certifications with exact service boundary and attestations, HAIEC's own audit engagement status, retention and region, third-party pentest promises, API key controls and operational monitoring. Provider SOC 2 does not certify the HAIEC SaaS product. Require authorized security/privacy/legal review before publication.
4. **Platform plans vs reachable product.** Pricing, Trust and marketing refer to kill switches, continuous monitoring, MARPP, audit logs and AI scanning. Reuse the existing 76-activity UI/API/MCP/owner availability reconciliation and source-gated truth. A commercial tier does not itself prove active operational control/enforcement.
5. **GitHub Action claim on homepage.** Main homepage labels a GitHub Action in its workflow row while lib/developer-integration-source-status.ts marks the standalone HAIEC GitHub Action v2 NOT_RELEASED. Distinguish GitHub App, future local Action and unrelated open-source scanner package actions. Verify exact link/ref and actual release before keeping availability messaging.
6. **Standalone tools.** /developer-security still uses source/boundary/runtime as layers though the 3 MIT tools are independent. /mcp-tenant-isolation still advertises 0 vulnerabilities, 203 passing tests, universal competitor absence and provenance-signed scan claims. Its shared page client already improved --path scan examples in Main, but package action.yml source and exact release behavior need targeted separate acceptance. /llmverify still advertises universal prompt-injection blocking and generic runtime monitoring despite bounded pattern checks and optional local audit. AI AppSec's new hero is in Main but the npm v0.1.0 versus repository-source v0.1.1 and actual stdio CLI/MCP setup should be verified. Reuse Page #25, #27, #28, #29 plans; no new redesign.
7. **Evidence/integrity and legacy MARPP.** Canonical evaluator is evidence/claim/snapshot/version bounded, not a guarantee all reissued raw receipt bytes share one identical hash. Current /marpp marketing outside indexable registry says 100% immutable and universal PostgreSQL guarantees; legacy code/docs conflict on acronym expansion and actual scopes. SQL protects specific evidence fields and audit table operations when applied, not all physical records against every privileged actor. Canonical Decision Receipt integrity is a DIFFERENT owner. Plan a precise correction and route governance for this page.
