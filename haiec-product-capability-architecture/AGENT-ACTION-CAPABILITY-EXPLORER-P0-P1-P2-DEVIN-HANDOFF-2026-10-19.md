## Decision
**Promote existing analysis, do not rebuild it.** Make the customer-facing question immediate:
> **How many agents did HAIEC discover? What can each one do? Which actions are consequential, who may authorize them, what was observed, and what remains unproven?**

"Agent" counts must be explicitly qualified as *source-discovered agent definitions/candidates*, not running instances or MCP references. A zero when analysis was not performed must read **Not analyzed**, not zero. An action candidate cannot become an authorized, effectively granted, reachable or observed action merely through UI composition.

### Specific current UX/correctness pain
1. `SystemWorkspace` primary tabs (Overview/Sources/Evidence/Investigations/Assurance/Controls/Reports) expose `Action & Authority`, `Reach & Impact`, and `Repository Intelligence` only under **Advanced**. The Overview has an AI agent briefing but clicking the agents is not the dominant journey.
2. `AgentReachabilitySection.AgentCard` computes `agent.toolCapabilities.length` then labels it "capability stage(s)." This is **neither seven-stage count nor distinct consequential operation count**. The stage chain remains valid. Correct UX labeling/counting without changing canonical state.
3. `AgentInventoryItem` already exposes name, framework, source file:line, declared tool refs, qualified tool capabilities, handoffs, agent-as-tool, team routes, shared resource hubs, persistent creation, evaluation-integrity exposure, and limitations. Keep all and enable clickable per-agent access in Summary mode.
4. `agentReachability.summary.agentCount`, `agents.total/shown/truncated`, `repositoryIntelligence.agentCandidates` and MCP server reference counts serve different denominators. Explain and consistently derive each count.
5. Current `ActionAuthorityTab` correctly says CURRENT OBSERVED isn't established from that read model; do not promote historical U5 OBSERVED or configured telemetry into a current agent action fact.
6. `AgentReachabilityReadModel` explicitly holds model-boundary identity at PARTIAL when it cannot prove association to an exact agent; don't render this as agent-dispatched/agent-executed.
7. Provider EG-1 gives partial IAM context but no general per-action canonical EFFECTIVELY_GRANTED facts; avoid "allowed" badges from coarse policy or IAM matching.
8. Control catalog contains 45 profiles (including 3 specialized tests); visibility implementation is a subset and does NOT imply executed/evaluated for this selected agent/action. `control-visibility/index.ts` is a thin reader.
9. P2 comparable changes should reuse evaluation-based consequence delta; stable semantic identity requires exact owner-validated source/operation tuple. `candidateRef` sequence IDs are scan-local; cross-scan heuristic identity is forbidden.
