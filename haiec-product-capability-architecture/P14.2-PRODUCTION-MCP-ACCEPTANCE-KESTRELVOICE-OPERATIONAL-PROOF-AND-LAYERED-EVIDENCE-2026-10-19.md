## 1. Stage A — narrow acceptance integrity (R01–R04 closed)

### R03 — `neg:bogus-section` exact code

The acceptance client previously passed any `isError` or 404. Now requires `isError === true` **and** `code === 'SECTION_NOT_FOUND'`. `CODE_VERIFIED` in `artifacts/_p14-mcp-client.js`.

### R04 — dev credential helpers fail closed

`_p14-mint-key.js` and `_p14-revoke.js` now refuse non-loopback/non-localhost targets and require a development/E2E environment — dev test-auth can no longer be pointed at arbitrary or production endpoints. Client environment classification is derived from the target URL, not an arbitrary `P14_ENV_CLASS` string. `CODE_VERIFIED`.

### R02 — retrieval-guidance honesty

The bounded-mode comment/retrieval string implied indexed verification items were reachable via the `section` selector. Corrected: `section:"<id>"` returns **one persisted section body** only; verification-item and insight payloads are **not independently retrievable** unless a future tool supports it. `CODE_VERIFIED`, single-line doc fix in `lib/mcp/server.ts`.

### R01 — large-report boundary measured, not guessed

`detail:"bounded"` retains `narrative`, `questionDisposition`, `verificationItemIndex`, and `resolutionGroups` verbatim-ish — so whether bounded itself can exceed the 160k budget was a real open question. Measured on generated fixtures (`TEST_VERIFIED`, mcp-assurance now **133/133**):

| Source report | Items | Full serialized | Bounded read | resolutionGroups | Result |
|---|---|---|---|---|---|
| ~259KB | 80 | ~259KB | ~29.9KB | ~16.1KB | delivered under budget |
| ~316KB | 120 | ~316KB | ~36KB | ~22.3KB | delivered under budget |
| ~373KB | 160 | ~373KB | ~42.1KB | ~28.4KB | delivered under budget |
| ~1.3MB (extreme) | ~400+ | ~1.3MB | >160KB | dominant | honest `RESULT_TOO_LARGE` |

**Boundary established:** a realistic oversized report resembling the original (~160–400KB source, ~80–160 verification items) is delivered by `detail:"bounded"` well under the 160k cap with exact omission counts and complete indexes. Only pathological cardinality (~400+ items / >1MB source) tips bounded over budget — in that case the tool returns `RESULT_TOO_LARGE` explicitly, points at `section` retrieval / `haiec_explain_evaluation` / summary, and **never silently truncates**. The 160k global cap was not raised. `TEST_VERIFIED`.

## 3. Stage C — KestrelVoice operational journey — `LIVE_VERIFIED` 16/16

**Independent external client** (`artifacts/_p142-kestrel-client.js`, committed) exercised the **production** `https://kestrelvoice.com` surface — real HTTP, no handler invocation, no shared credentials with Devin's own auth. All secrets passed via environment variables only; none printed, none committed.

**Tenant:** `qa-owner` — "QA Hardening Tenant" (isolated, purpose-built QA tenant; dedicated test user `qa-owner@dev.kestrelvoice.com`; configured `QA Receptionist`, before-greeting `"Thanks for calling the QA tenant."`).

### Chain verified end-to-end (`LIVE_VERIFIED`)

1. **Real QA user session** — service-role session mint for the dedicated QA test user (authorized test-user path, same class used in earlier authorized QA work).
2. **OAuth 2.1 DCR** — `POST /oauth/register` → dynamic client.
3. **Consent** — `/oauth/authorize` consent token issued; approve POST → `303` redirect with authorization code (PKCE S256).
4. **Token exchange** — `POST /oauth/token` → resource-bound JWT, scope `mcp:read mcp:write`.
5. **MCP initialize + tools/list** — `kestrelvoice-mcp`, **69 registered tools**.
6. **Reads:** `get_account_status`, `get_agent_summary` (QA Receptionist), `get_agent_configuration` — all `isError=false`, digest-recorded.
7. **`preview_agent_update`** — `{changes:{greeting_message:<test value>}}` → durable pending-approval action, `apply_with` exact-arguments binding, `approval_url`, `expires_in_seconds`. Preview created **only** the pending record — no config mutation (verified by readback before approval).
8. **Negative control** — `apply_agent_update` **before** approval → `APPROVAL_REQUIRED` exact code. Preview token alone does not authorize application.
9. **Human approval** — canonical `POST /api/mcp-actions?action_id=…` with the authenticated QA-owner session + CSRF → action approved. (Mechanically identical durable record to an in-UI click; see gate caveat in §5.)
10. **`apply_agent_update`** — applied; `persisted_values` returned.
11. **Readback after apply** — `get_agent_configuration` shows the test greeting persisted. `match=true`.
12. **Revert** — second preview → approve → apply restores the original greeting; readback `restored=true`. QA tenant left in before-state.

**Two client bugs found and fixed during the run** (harness-side only, not product defects): `confirmation_token` lives under `apply_with.arguments` (not top-level); `action_id` is base64url (not hex). Kestrel error bodies are JSON `{"error_code":…}` (not `CODE:` prefix) — parser updated.

**Evidence:** `artifacts/_p142-kestrel-evidence.json` = **2.1KB** — run id, timestamp, environment, 16 case statuses/digests only. Fully separate from HAIEC evidence files.
