Three questions to keep separate

A model, an agent and a consequential action are not the same thing.

A language model computes outputs from an input context. An agent runtime can use those outputs to select tools, continue workflows and affect external systems. The security question changes depending on which component you can actually observe.

Model behavior

What did the LLM produce?

Model identity, request context, generated response, usage, latency, quality checks and changes across comparable tasks.

Agent orchestration

What did the application do?

Trigger, prompts, RAG context, tool selection, SDK events, authorization, executed tool calls, retries, handoffs and responses.

Consequence assurance

What could happen, and who authorized it?

Supported reachability, indirect action paths, business decision authority, control evidence and any qualified target-side outcome.

Configuration and retraining, explained

Changing the prompt is not retraining the model.

Organizations can update the context and tools an AI uses without changing its trained parameters. Keeping these paths separate helps explain what changed when quality, behavior or consequences shift.

Foundation training

Pretraining

Large-scale training establishes model weights. Evidence may include training jobs, datasets, checkpoints and artifact lineage when controlled by the operator.

Parameter update

Fine-tuning

Additional training changes weights or adapters. New model versions and release evaluation should be tracked independently.

Inference-time context

Prompts and RAG

Instruction templates, retrieval and memory change what the model sees for a request, normally without changing underlying weights.

System behavior

Agent configuration

SDK, tool schemas, gateways, credentials, retry policies and approvals determine what the surrounding application can do.

Practical distinction: A customer can see the prompts and outputs at its own application boundary even when using a managed model API. Self-hosting adds possible training/weight/serving diagnostics, not a guaranteed readable record of the model's internal thoughts.

Why a configured guardrail is not the entire story

Different controls act at different moments.

A model output guardrail can evaluate generated content. Tool authorization and business-side enforcement operate elsewhere. The same system may need separate checks for a data response and a financially consequential action.

01 InputBefore inference

Validate inputs, authorize requests and handle sensitive content.

02 Model outputBefore display or use

Validate content, format and policy-relevant output where enabled.

03 Tool and gatewayBefore execution

Bind principals, arguments, scope, approvals and guardrail decisions to the exact action.

04 Target effectAfter or at apply

Use native provider/DB records to establish what actually changed or was prevented.

A tool can be allowed by IAM while its selected recipient or target still requires separate business authority. HAIEC's Delegated Action Integrity compares that decision context with source capability and relevant observations.
The consequence gap HAIEC is built to address

A model may respond correctly, an SDK may execute an allowed tool and the gateway may accept an API call. None alone establishes whether the resulting business choice was entrusted to the agent, or whether the action produced an external effect.

Frequently asked questions

What can we really see inside an AI system?

Can HAIEC inspect an LLM's internal reasoning?

There is no universal, faithful internal thought transcript to read. Managed providers expose only contracted signals. Self-hosted models may permit deeper low-level instrumentation, but logits, activations and interpretability probes are not equivalent to a readable explanation of every decision.

Can we observe an agent using a managed model?

Yes, when the customer owns or can instrument the orchestration, SDK, tool gateway or downstream APIs. Hosting the model elsewhere does not prevent tracing the application-owned request and tool path.

Does self-hosting a model make the whole agent visible?

No. The agent's orchestration, tools and downstream systems may be owned by another service. Model hosting and agent hosting are independent access questions.

Does prompting or RAG retrain the model?

No. They change inference-time context. Actual training or fine-tuning modifies a model artifact and should be tracked through separate dataset and version evidence.

Can model drift prove an attack or poisoned training data?

No. Version, statistical, token or output drift can signal a difference worth investigation. Attack attribution and training-source compromise require additional qualified facts.

Can model API logs reveal full prompts and outputs?

Only where the customer/provider has enabled and authorized that content collection. Retain sensitive content in the customer-controlled source where possible and use qualified references and hashes for assurance.

Can a provider guardrail prove the agent's tool was safe?

A model input or output check addresses its configured content scope. Tool parameters, delegated business choices and downstream effects require their own authorization and evidence.

What about retries, queues and multi-agent handoffs?

They may move a consequential operation across processes and time. HAIEC can analyze supported source paths and correlate connected observations when stable action identities and qualified records are available.

Why use deterministic HAIEC assurance instead of another LLM?

An AI assistant can help operate or explain an assessment. HAIEC's canonical conclusion comes from recorded rules and evidence within a defined evaluated scope, not from a model's subjective description.

Do we need every data source before seeing a finding?

No. Supported code and configuration evidence can identify a meaningful consequential exposure. Other evidence sources help answer additional specific questions when needed.
