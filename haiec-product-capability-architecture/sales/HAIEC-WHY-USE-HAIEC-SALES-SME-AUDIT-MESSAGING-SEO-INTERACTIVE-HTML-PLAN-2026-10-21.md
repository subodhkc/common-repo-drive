## 1. Buyer-first findings

Buyers most often approach HAIEC because a concrete decision or action is hard to defend. Lead with questions, not the engine internals:

- Our AI pilot works but the CISO/board is not ready to authorize release.
- We have agent permissions but do not know what a tool call could actually change.
- A vendor AI might operate across our ERP, data, identity or customer systems.
- We want controls, but need evidence they apply to the agent and operate at the relevant boundary.
- Security tests and model evaluations pass, but they do not resolve real business action authority.
- The regulator, procurement auditor or customer is asking for defensible technical facts, source provenance and exclusions.
- We need to investigate a possible unintended agent action without declaring a confirmed exploit from a source path alone.
- A code or tool permission update invalidates confidence in an earlier evaluation.

**Main sales frame:** "Your AI works. Can you prove it is ready for real-world decisions?" The buyer's real need is an evidence-backed answer to a consequential action question.

**Supporting distinction:** "AI can help you perform an assessment. It should not decide its own safety based on an opinion. HAIEC evaluates supported evidence deterministically and leaves unknown facts visible." This is a positioning claim about the core assurance process, not a claim HAIEC never uses model-assisted flows or authorized runtime adversarial testing.

**Commercial wedge:** One consequential AI system, one priority question and explicit evidence needed to answer it. Start with available source-backed findings before IAM, policy or runtime evidence is complete; additional sources can strengthen separate claims. Never imply ALL evidence planes are prerequisites to early source findings.

### Core objection handling

**We already run security scanners:** HAIEC can connect qualified component findings to agent action paths and authority boundaries. It complements scanners, not replaces them.

**We have GRC and AI policies:** Policies express intended authority. A source path and effective credential rights answer different questions, and neither by itself proves a customer target guard works.

**We have no runtime telemetry:** Start with source-backed findings. Do not imply live behavior was monitored; request additional evidence only for claims that require it.

**Can you guarantee safety or block all agents?** No universal safety or native enforcement claim. Show actual configured interception/dispatch/target evidence only when implemented and tested in customer context.

**How can we trust a report?** Frozen evaluation, producer/provenance, explicit limitations and actual issued receipt verification. Integrity is not proof every upstream assertion is true.

## 6. Positioning against adjacent software without feature wars

Competitors in broad AI governance emphasize inventory, accountability and policy; agent security vendors often emphasize agent discovery, runtime protection and threat response. HAIEC should lead with **Consequence-First Deterministic AI Action Assurance** and its exact source/authority/observation/report boundaries.

- **Versus AI model testing:** A model's response under test is not the whole agent's real tool authority or potential business effect.
- **Versus SAST/DAST:** Rule matches alone are not a fully joined agent action and business consequence; source reachability remains bounded and can be reported immediately.
- **Versus GRC:** Policy and program records matter, but do not establish actual code paths/permissions/runtime effects.
- **Versus IAM/PAM:** Technical credential grants alone do not determine the agent's entrusted business discretion.
- **Versus SIEM/observability:** Events are useful but can miss what source permits or what remains unknown; fresh source does not equal complete coverage.
- **Versus independent certification:** HAIEC supplies scoped technical evidence and reports. Human assessors own independent audit opinions and any certification.

No unsupported superiority claim or assumption competitors lack capabilities.

### Five purposeful diagrams

A. **Agent to business effect:** source agent -> tool/API -> protected resource -> possible consequence, with a visually separate runtime and independent target-witness proof state.

B. **POC-to-production assurance:** proof-of-concept -> relevant first finding -> authority/evidence review -> accountable human decision -> conditional monitoring/verification. Illustrative, not always a strict sequence.

C. **Five peer evidence planes:** Requested, Policy Authorized, Effectively Granted, Code Capable, Observed. DAI applies cross-cutting to selected choices. A supported source plane cannot silently fill unknowns in others.

D. **Complementary enterprise stack:** scanners, IAM, GRC, telemetry show different facts that HAIEC can evaluate together when qualified; it does not replace them or guarantee current connectors.

E. **Actual proof package:** action map -> bounded report -> unresolved evidence list -> issued U6 receipt/integrity when available, with links to public source sample and not fictional "verified" badge.

Style: Light theme, elegant minimal geometric SVGs, subtle animated dashed edges, real DOM titles and labels, reduced-motion equivalent, desktop/mobile, no external scripts or telemetry in standalone preview, static-print legibility and no em dashes.
