Architecture02 · Technical proposition
Technical proposition

What HAIEC does. What it does not do. How to read the status labels.

Status legend Demonstrated · persisted evidence Supported pathway Evidence-dependent Preview / held Scenario simulation Cataloged / proposed Not established

What HAIEC does

Establishes consequential actions an AI system can cause.
Compares requested, policy-authorized, effectively granted, code-capable and observed authority.
Evaluates deterministic controls against qualified evidence.
Records human decisions with digest-bound receipts.
Surfaces what remains unknown, unassessed, or held.

What HAIEC does not do

Does not replace IAM, SIEM, AppSec or GRC.
Does not certify compliance — framework mappings are context.
Does not guarantee runtime enforcement — native adapters are per-target.
Does not issue a safety verdict — dispositions are scoped to evidence.
Does not silently promote uploads to detector evidence.

What makes HAIEC different

Deterministic, not LLM-in-the-loop
Assurance engine evaluates fixed rules against qualified evidence. Same input, same result, same digest.
Authority-to-action, not just access
Compares what was approved, granted, code-capable, and observed. The gap is the finding.
Lifecycle, not one stage
Pre-deploy, release, runtime, and audit share the same evidence spine.
Honest about gaps
NOT_ASSESSED never downgraded. Frontier items named. Held features labeled before a CISO asks.

Architecture06 · Five planes + DAI
The authority gap

Five independent evidence planes. DAI as a separate comparison — not a sixth plane.

01
Requested
What the AI system asks to do.
02
Policy-authorized
What the business permits.
03
Effectively granted
What credentials actually allow.
04
Code-capable
What code can reach.
05
Observed
What runtime evidence shows.

Comparison, not sequence

The five planes are independent assertions. HAIEC does not require them to be supplied in order, and does not require all five to reach a finding. A single-plane evaluation is valid — it just names fewer established facts.

The mismatch is the finding. Requested but not policy-authorized → business policy gap. Policy-authorized but not effectively granted → provisioning gap. Effectively granted but not code-reachable → dead privilege. Code-reachable but not observed → latent exposure.

DAI — nine orthogonal dimensions

OPERATION
action semantics
TARGET
resource or entity
SCOPE
tenant, domain, boundary
MAGNITUDE
amount or volume
DURATION
time window
APPROVAL
human authority
DATA_CLASS
sensitivity tier
ENVIRONMENT
prod / staging / dev
GEOGRAPHY
jurisdiction or region
Delegation ≠ a sixth plane. DAI compares a delegated chain against the policy that authorized it. The five planes describe authority classes; DAI describes narrowing or widening at a specific delegation hop. Both are required to answer the authority question.

Disposition is not authorization
An assessment may produce ALLOW / REVIEW / BLOCK only within the evaluated claim and configured decision semantics. It is not permission to deploy. It is not a certification. It is not a runtime enforcement action. Each of those is a separate layer.

Proof frontier — always visible

Every evaluation ships with an explicit NOT_ASSESSED list. Missing evidence is never scored as zero risk. Frontier items name the exact producers, sources, or registry entries that would close them.

What "reproducible" means

  • ·Same input scope → same findings
  • ·Same findings → same digest
  • ·Change one byte of evidence → digest invalidates
  • ·No LLM in the verdict path

AI AppSec — separate package

Static analysis for AI application code. A distinct developer package, not automatic SaaS assurance.

Detectors
122
Rule definitions in the AI AppSec security package
Security checks
79
Grouped into observable findings across AI-specific code patterns

What it examines

  • ·Unsafe AI-output execution — model output fed into shells, SQL, templates, or eval
  • ·Prompt and RAG trust boundaries — untrusted content flowing into system prompts
  • ·Exposed secrets — API keys, tokens, credentials in source
  • ·Insecure API usage — permissive CORS, weak auth, missing rate limits
  • ·AI-specific vulnerabilities — tool exposure, memory risks, output handling
Separate package, not an automatic pipeline. The 122/79 AI AppSec package can operate independently of the SaaS assurance surface. It does not automatically feed the core Assurance Engine unless a qualified integration route exists. Its findings appear as AI AppSec output, not as HAIEC-verified control results.
The distinction matters. A source-code finding is a claim about a file. It becomes an assurance finding only when that file is part of a qualified evaluation scope. HAIEC preserves the boundary in both its API and its UI.

DevSecOps14 · Runtime adversarial testing
Runtime adversarial testing

Model claim ≠ tool execution ≠ external effect. Three separate statements per test.

What an authorized endpoint test can establish

Prompt injection
Does the model follow injected instructions when content is treated as data? Bounded finding.
Tool forcing
Can an attacker cause a tool call the agent would not normally make? Bounded by test scope.
Role confusion & leakage
Does the model reveal context, change behavior under role framing, or expose sensitive info? Bounded by prompt set.
1
Probe sent
Authorized endpoint · operator consent · scope pre-declared
↓
2
Model response
What the model returned — a claim, not a fact about the tool
↓
3
Tool call observed
Did a tool get called? Would require qualified telemetry to confirm
↓
4
External effect
Did anything land at the target? Requires independent readback — separate from tool execution
Not every probe is a test. Runtime endpoint testing is opt-in. It requires an authorized endpoint, operator consent, and bounded scope. It is not passive continuous monitoring. A model claiming "I will call tool X" is not evidence that the tool was called. A tool being called is not evidence that its effect landed.

DevSecOps15 · Monitoring & drift
Continuous monitoring

Baseline vs current, with source health visible. An anomaly is not a breach.

What monitoring observes

  • ·Agent tools & permissions — new tool, changed scope, new identity
  • ·Actions outside approved scope — resource, magnitude, target divergence
  • ·Identity & delegation — chain continuity, credential reuse, handoff gaps
  • ·Token / usage / cost — deviations against comparable baseline
  • ·Guardrail & alert — decision + denial + delivery evidence
  • ·Source health — freshness, continuity, coverage gaps

Source health is visible next to every signal. Stale evidence cannot establish detection coverage for its own source. Other connected sources may still generate alerts. Silence is never proof of safety.
What monitoring establishes
A qualified signal was observed at a specific time, from a specific source, against a specific baseline.
What monitoring does not establish
That a breach occurred. That an alert was acknowledged. That the underlying source is complete or continuous.

What exists in HAIEC source
Execution guard code. Kill-switch foundation. Intended native adapter contract. Human authorization workflow. Alerting framework. The pathway for a response.
What is not universally wired
Native enforcement adapters per target provider. A production-wide automatic enforcement guarantee. Universal kill-switch coverage across every AI system.
Assessment BLOCK ≠ physical stop. A disposition of BLOCK means the evaluation found evidence outside approved scope. It does not mean the target refused the action. Dotted arrows are honest arrows. Any intervention step that requires target-native integration is drawn dotted. It communicates "the pathway exists" without claiming "the pathway is wired." A CISO can see exactly where the boundary is.

What the reviewer can do

Approve as scoped
Binds the exact scope and digest. Expires at declared time. Reversible until revoked.
Approve with conditions
Names specific conditions, due dates, and consequences of failure. Weaker than full approval.
Reject with rationale
Requester sees the reason. Rejection is a valid outcome, not a failure.
Request changes
Returns to requester without approving or rejecting. Preserves the request.
Approval ≠ authorization to deploy. It is a named human's decision about a requested scope. Deployment, target enforcement, and effect verification are separate operations with their own evidence requirements.

Scoped enterprise POC · acceptance criteria (commonly 4–8 weeks after readiness)
  • Scope: one consequential AI system, one business owner, one technical counterpart, one named risk question.
  • Access: source repository or archive, operating envelope or intent, IAM grants (live or export), optional 7–14 days OTLP.
