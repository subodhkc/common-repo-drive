## Decision in one paragraph

HAIEC can provide *general deterministic authorization contracts, governance, evidence identity, next-action readiness and inspectable evidence* without bespoke business-rule engines for each customer. **Physical blocking always requires an enforceable control point under customer/provider control.** Offer **(A) existing API/MCP/gateway or native policy integration (preferred)**, **(B) thin application middleware/SDK where traffic cannot be routed**, or **(C) native provider policy/permission and receipt-based reporting**, with a single provider-neutral HAIEC contract. A customer chooses which trusted point can intercept the precise tool/mutation. Build a tiny contract + one non-production real interceptor first; broad arbitrary-agent enforcement is **NOT_SHIPPED**, a policy decision is **NOT** proof of a customer block, and a screenshot is **NOT** an independently attested target outcome.

## 4. Minimum skeleton to build without customer-specific rules (proposed interfaces, NOT existing API)

A single **Action Attempt Envelope**, **Decision response**, and **Execution/Outcome witness**. Reuse canonical data shapes rather than create duplicate databases.

```ts
// DESIGN-ONLY: NOT A SHIPPED API OR SDK. Names illustrative; reconcile with
// NativeDispatchRequest, ControlInvocation, OperatingEnvelope and UCP owners.
type ActionAttempt = {
  organizationId: string; aiSystemId: string;
  attemptId: string; idempotencyKey: string; correlationId: string;
  actorPrincipalId: string; delegatedByRef?: string;
  operation: string; targetResource: string; environment: string;
  inputDigest: string; // canonical digest of all decision-relevant fields
  amount?: { currency: string; decimalString: string };
  requestedAt: string; deadlineAt?: string;
  enforcementPointId: string;
};
type ActionDecision =
  | { kind: 'ALLOW'; decisionId: string; policyDigest: string; expiresAt: string;
      actionDigest: string; allowedTarget: string; evidenceRefs: string[] }
  | { kind: 'DENY'; decisionId: string; reasonCodes: string[] }
  | { kind: 'REQUIRES_HUMAN'; requestKey: string; requestVersion: number;
      requestDigest: string; expiresAt: string }
  | { kind: 'INDETERMINATE'; reasonCodes: string[] };
// Critical boundary: INDETERMINATE is NOT permit. Pending human review has
// NO dispatch permission; only a future revalidated, one-shot ALLOW can execute.
type EnforcementOutcome = {
  attemptId: string; actionDigest: string; enforcementPointId: string;
  actualGuard: 'ALLOW' | 'DENY' | 'NOT_EVALUATED';
  providerAck: 'ACCEPTED' | 'REJECTED' | 'UNKNOWN';
  targetEffect: 'VERIFIED' | 'NOT_VERIFIED';
  qualifiedEvidenceRefs: string[];
};
```

**No global customer configuration requirement:** adopt a small typed per-adapter manifest (operation, target kind, identity source, key/credential scope, semantic fields, allowed payload size, side-effect grade, supported modes, receipt format, fail mode, idempotency, timeout, freshness, bypass routes). HAIEC can discover likely operations/source nodes and suggest mappings, but an authorized human/provider must verify the target mediation seam. Unknown target capability → NOT_WIRED, never 'Protected'.

**Conditional approval policy:** Express via existing Operating Envelope rules and My Work, but treat human approval as an **obligation** requiring trusted fulfillment on a *subsequent* invocation, not a magic global boolean. Avoid `ALLOW` just because an earlier approval exists. For a deferred tool call, choose either (A) release a verified queued operation through an authorized execution owner with atomic claim, or (B) require caller to re-submit the exact request after approval; B is safer for the first skeleton. Never auto-resume on receiving an unauthenticated webhook.

**Policy evaluation strategy:** Keep HAIEC canonical authorization mapping/digests and existing deterministic evidence plane owners. For hot-path execution choose a **local/cacheable signed/distributed policy snapshot** or a customer-native Cedar/OPA PDP where supported. If HAIEC cloud is down, do not silently allow high-impact actions; specify per-operation deny/hold/unavailable behavior and maximum permitted snapshot age. Do not introduce every remote U5 scan into tool invocation latency.

- SLA/safety engineering only after measured tail latency/error budgets; availability mode explicitly per action.

### Required negative tests

1. Unregistered target or missing endpoint → deny/NOT_WIRED; no direct bypass.
2. Foreign org/system/credential, forged/missing actor, mismatched recipient, wrong environment → denial and non-disclosure.
3. DRAFT, stale/revoked approved policy, expired human decision, conditional obligations unsatisfied → no permit.
4. Pending/rejected approval → no execution; human requester cannot self-approve; copied MCP instructions cannot authorize.
5. Attempt payload changes after approval, TOCTOU/time-of-check, policy revocation during hold → demand fresh decision.
6. Duplicate/replayed requests, concurrent workers, retried callbacks, returned 200 without guard decision, lost Redis → no unauthorized duplicate effect; show UNKNOWN where atomicity isn't proven.
7. Unknown decision/timeout/target unavailable/network partition → high-impact deny/hold (not default allow), operator-visible reason.
8. Partner OPA/Cedar policy and target cache digest mismatch → fail closed; correct release/recovery semantics.
9. Fixture result cannot be promoted to customer LIVE_PROTECTED; no fabricated effect or replay-derived live test.
10. Exactly one changed field, source event-time drift, missing readback, two same-name targets/systems → wrong attribution refused.
11. PEP is actually on every tested path; credential-only direct API attempts cannot bypass the gate.
12. Bounded log redaction: secrets and regulated source content absent from audit/records, action fingerprint always bound.

**Definition of done for skeleton:** real test tool operation blocked before its handler, pending operation never executes, human decision recorded with CAS, subsequent valid exact request succeeds **once**, target/ledger output shows actual result, negative bypass cases, evidence and System Workspace show *NON_PRODUCTION_FIXTURE* rather than live protection. Without a real target, a published `npm install` example is not success.

## 6. Operational UX and user-facing availability (no new page)

- **Understand:** Action Map/Source onboarding shows which specific tools/targets are candidates and whether a real enforcement point is reachable/verified.
- **Assure:** Shows intended vs approved vs granted vs code-capable vs observed and per-action risk/proof frontier, not an execution permit.
- **Authorize:** My Work decision packet + scoped human approval/revoke/expiry; optional operator-selected policy export to supported PEP, separately verified installed digest.
- **Monitor:** Explicit sources, freshness, policy mismatch, action attempt, decision, guard outcome, provider ack, true target-effect proof, missing receipts and alerts; no proof from absence of logs.
- **Protect:** Existing Controls/System Workspace operations block / Kill Switch; **one “Enforcement connection” sub-section**, not a new top-level app: integration kind, current native/partner status, specific mediated operation, policy match, last trusted decision, latest target guard/receipt, fail mode, bypass test result and one permission-bound setup action.
- **Verify:** Frozen U5/U6 evaluation/report and independent replay/target readback, exact target/event identity and changes since as-of; a replayable Control Test isn't target enforcement.

**Customer-safe states:** `Not connected`, `Configured, unverified`, `Connected, policy match unknown`, `Test fixture only`, `Approved, target not wired`, `Mediation witnessed`, `Block witnessed`, `Target effect independently verified`, `Unavailable/unknown`. Treat these as **display projection descriptors**, not mandated new DB enums. UI, REST, MCP must derive from same E5/E6/E4 persisted sources.

**Recorded operational journey** (future separate external-client qualification): source/target registration → principal authorization → frozen policy+decision identity → preflight → attempted action → issued local decision → actual gate refusal or hold → human review → fresh re-submission → guard acknowledgment → target readback → monitor/receipt/revoke/retest, with raw restricted capture and separate narrated/edited/captioned layer-wise video. Synthetic and live branches never mixed or silently described as production.
