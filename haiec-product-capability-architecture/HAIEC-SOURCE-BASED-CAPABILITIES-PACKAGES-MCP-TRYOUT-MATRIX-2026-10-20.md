## 1. Layered HAIEC product model: what is being sold

**Platform** = Evidence-Bound Assurance for consequential AI. **Not** one generic AI risk score and **not** one “AI scans AI” verdict. Canonical deterministic decision is scoped to a persisted Evaluation.

### Six independently selectable operating capabilities
| Job | Value to customer | Representative product owners / artifacts | Marketing boundary |
|---|---|---|---|
| **Discover** | Know what is connected, visible and source-capable; see meaningful consequence surfaces | AI Systems, source registry/binding, System Constellation, agent trace & action/access map | declared / registered / code-capable / observed are different; no universal inventory |
| **Evaluate** | See which relevant claims are established or uncertain; find control and authority divergence | SaaS static + authorized runtime testing, source reachability, canonical Assurance evaluator, five planes, DAI where qualified, control catalog | qualified evidence only, known gaps, status and scope; rule count != assessed coverage |
| **Authorize** | Put sensitive operating decisions under accountable human review | My Work / approval owners, operating envelope draft/approved distinction, decision receipt context | human dashboard approval is not proof an external tool enforced it |
| **Monitor** | Understand source health and conditional runtime change/operations | existing P10 monitoring read views, qualified telemetry, sources/coverage, investigations and response cases where wired | connected source freshness vs actually instrumented activity; not global native monitoring |
| **Protect** | Add controlled action boundaries for selected customer operations | kill switch SDK/guards, E5.1 enforcement-read model, E5.2 custom PEP integration scaffold | generic no-bypass target PEP/effect not universally wired or proven; customer-specific scope |
| **Verify** | Retrieve evaluated findings, receipts and report integrity, including limitations | Master Assurance Report, Agent Audit, U6 Assurance Package/Receipt/Public Verification, Passport | hash/receipt verification does not prove source truth or actual downstream target effect |

**Three pillars:** Understand / Assure / Govern & Operate are information architecture, not another pricing axis. **Five evidence planes** are independently evidenced dimensions; DAI delegation comparison is orthogonal to them, not a guaranteed “third-party authentication” event. Evaluate and Verify may depend on actual evidence and entitlements; “independent job” does not mean credential-free.

### Key objects customers can *see*
1. **AI System and Source Status:** named scoped subject and verified repository/source, not raw URL trusted by assertion.
2. **AI Action & Access Map / System Constellation:** supported source-derived agent → tool/handler/resource/consequence relationships and frontiers.
3. **Evidence Planes & Delegated Action Integrity:** requested vs policy authorized vs effectively granted vs code capable vs observed; delegation chain and source strength separate.
4. **Assurance Evaluation:** same qualified/frozen basis → deterministic bounded findings and ALLOW / REVIEW / BLOCK *within evaluated scope*, not universal safety.
5. **Agent Audit + Master Assurance Report:** evidence-backed answers, source identity, control/verification items, unknowns and exact evaluation links; reports reuse canonical truth.
6. **Human Decision / Verification Package:** accountable decision where configured; signed/hashed integrity only as exact artifact claims allow; public verification where issued, not always published.
7. **Qualified Ops Monitoring:** connected source health/observations; response cases and effect proof only where actually emitted/integrated.

**Marketing proof contract:** Each customer example must name source, evaluated time/scope, producer, qualified result, unknown, next step and whether the display is **REAL VERIFIED**, **SYNTHETIC**, or **CONCEPTUAL**. All synthetic examples explicitly labeled. Do not use numeric catalog size to signal coverage.

## 4. Low-friction MCP onboarding — product fact vs CTA

**Actual server:** \`https://www.haiec.com/api/mcp\`  
**Transport:** Remote stateless Streamable HTTP.  
**Authentication:** HAIEC scoped API key in \`Authorization: Bearer <HAIEC_API_KEY>\`. This is **not OAuth**.  
**Trusted links:** https://www.haiec.com/docs/agent-integration , https://www.haiec.com/developers/mcp-playbook , https://www.haiec.com/dashboard/api-keys and https://www.haiec.com/dashboard/ai-inventory.  
**Required scope:** tenant membership and authorized key per selected operation; public sample can be read separately without private key if page allows. Never paste key into chat, URL query, public client JS, screenshots, prompts or README.

### Correct public-facing CTA
**Headline:** \`Already using an AI coding agent? Let it operate HAIEC.\`  
**Body:** \`Connect the HAIEC MCP server to a supported agent or IDE. Your assistant can check what your organization is ready to assess, use authorized sources, request an evaluation and explain exactly what HAIEC established. The assurance result comes from HAIEC's deterministic services, not the assistant's judgment.\`  
**CTA 1:** \`Connect HAIEC MCP\` → \`/docs/agent-integration\`  
**CTA 2:** \`Copy four-word starting prompt\` → \`Check my HAIEC setup\`  
**CTA 3:** \`See example assurance report\` → \`/sample-reports\`

**The critical friction boundary:** Merely typing “connect to HAIEC MCP” in any chatbot **does not grant it a connected tool/server or credentials**. Compatible client installation/configuration and key approval are prerequisite. Some clients can present a configuration UI or facilitate an authorized connection; others require manual MCP server settings. Advertising “one prompt, instantly assess any repo” is false.

### The honest 3-step user story
1. **Connect once**: Sign in/select org, create least-privilege API key from its secure dashboard and configure a supported MCP client with endpoint and bearer header in the client's private secret store. No public/token-sharing shortcut.
2. **Ask your agent**: \`Check my HAIEC setup\` → \`haiec_preflight\` (read-only). The tool identifies accessible systems and the exact next eligible action; it is allowed to say SETUP_REQUIRED. \`haiec_capability_guide\` can explain which goals are eligible.
3. **Evaluate only when ready**: Select existing system; use previously verified/bound source or obtain GitHub App authorization and trusted source binding (or qualified attached local scan), exact branch/consent and key scope. Then \`Assess my AI agent\` → \`haiec_run_assurance\` with an idempotency key; inspect exact run/evaluation, Agent Audit, Master Report, unknowns. **Write/setup/test/upload actions need explicit user confirmation**. No unrelated forced telemetry or questionnaire.

**Copy alternatives that are truthful:**
- \`Your agent guides. HAIEC evaluates.\`
- \`Ask what the evidence supports.\`
- \`Start with your existing repo, when authorized.\`
- \`Connect your tools. Keep the proof boundary.\`
- \`Read-only setup check first. No scan until requirements are satisfied.\`

### Better trial surface design
A narrow, copyable MCP setup strip across Platform and Products with:
- **Endpoint** (copy, no secret): \`https://www.haiec.com/api/mcp\`
- **Prompt** (copy): \`Check my HAIEC setup\`
- **Client selector** that changes *documented steps*, e.g. Cursor / Claude Code / Devin / Other, not any hidden automatic configuration; link exact official documented guide.
- **Result preview** of *possible states* \`READY / SETUP REQUIRED / INSUFFICIENT SCOPE\`, each explicitly marked **illustrative**, never presented as a live successful preflight.
- **Next action** based on authentic returned preflight; front-end animation/preview cannot authenticate or infer readiness.
- **Separate offline preview**: sample report and standalone local AI AppSec quick check are **not full HAIEC Assurance**; AI AppSec needs Semgrep and permission to install/run.

### Important MCP operational guardrails
- Read-only first. No automatic source registration/scan. \`haiec_create_ai_system\`, \`haiec_bind_github_source\`, \`haiec_run_assurance\`, upload, draft envelope, publish receipt and runtime tests require their actual API scopes and human/user-confirmation contract.
- A viewer key may preflight and read allowed summaries but cannot simply launch runs. AI System/binding is tenant-scoped.
- Reuse existing user's registered system and consent; missing telemetry is optional for static source assurance, but cannot support observed behavior.
- For active runtime tests \`haiec_runtime_preflight\` first and explicit consent; no auto “run red team everywhere.”
- MCP merely delegates to canonical services; no second LLM-based verdict, no global no-configuration “auto-discover all repo” promise.

## 5. Worked comparison — superiority by what is *demonstrated*

**Illustrative question:** “Can this support AI refund the wrong recipient?”

| Input/step | Other narrow tool might establish | HAIEC intended differentiating lens | Boundary |
|---|---|---|---|
| Security scanner | source code's API call and possible sink | connects source path to action target and defined consequence | does not prove it executed |
| IAM/policy | permission scope and written policy | keeps effective grant, policy and actual delegation separate | needs qualified policy/grant records |
| Trace/observability | specific emitted tool call in connected span | puts runtime observation beside code capability and approval evidence | no traces = UNKNOWN |
| Human governance | reviewer's intended permission | preserves documented scope/conditions and exact basis | receipt isn't target-side block |
| HAIEC evaluation | canonical bounded disposition, Agent Audit, proof gaps | links technical and executive decision with versioned evidence | not general safety certification |

**“Better” proof to prioritize:** one exact customer evaluation showing material consequence, a previously hidden delegated-authority gap, source-backed references, a human reviewer’s next step and honest UNKNOWN; then actual post-connection source and fresh-evaluation acceptance. Do not claim superior recall, accuracy, coverage, lower costs or deployed protection without comparison.
