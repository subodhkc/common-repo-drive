## Must-fix / check before real customer testing
**P0-A — exact subject-to-system binding and trustworthy metadata.** In `app/api/control-test/response-workflows/route.ts`, `subjectResolvable(org, subject)` checks if a `detf/...` finding or `ai_security_findings` row exists anywhere within organization; `aiSystemId` is checked separately; there is no exact finding/control-result ownership join to that system. Scanner branch accepts `ruleId` match; control result branch only checks resultId+org, not `controlId`/`controlVersion`. Caller provides subject `evidenceRefs`, `controlId`, severity, desired system. This can produce a technically persistent **misbound response case** even within one tenant. Implement canonical source-derived exact subject resolution with system/scan/eval binding, canonical control/version/severity/evidence refs, fail closed on missing certainty. If findings are only org/surface-scoped, show unbound/requires-qualified mapping rather than invite arbitrary system choice; no cross-system approval/retest contamination. Add negative tests for matching org/wrong system, same ruleId different findings, mismatched control, malicious evidence refs.

**P0-B — ACK bearer link disclosure.** The new POST route returns `ackUrl` from `notifyResponseWorkflow`; that URL includes signed `?t=...` single-use credential. The new UI ignores it but the network response to case opener can access it. Route comments assert ACK token material isn't returned (GET/MCP), not true for POST. Remove credential/link from ordinary POST response, avoid logging/analytics, keep delivery through secured recipient notifier. Check event logs, redirects, referrer/cache etc as appropriate. The authenticated ACK endpoint exists and is owner/admin-scoped, but do not hand out target-recipient token to ordinary case openers. Test no `ackUrl`/token in HTTP, MCP or logs. Avoid changing established UCP token verifier internals without necessity.

**P0-C — telemetry declaration provenance / false positives.** `runtime-correlation-input.ts` constructs `AriDelegatedAuthorityRelation` with `state:'ESTABLISHED'` and `principalBinding.bindingState:'RUNTIME_OBSERVED'` from span-supplied `haiec.delegation.*` and `gen_ai.agent.id` alone. Source data is self-reported; no independent principal/credential binding established. AR-03 compares two span claims; do not label *verified unauthorized delegation*. AR-09 uses a Set of `haiec.declared.model_call_surfaces` supplied **in the same ingest batch** and reports an unregistered model surface even if no authoritative registry was available: **absence-of-declaration != proof unregistered**. AR-20 egress compares destination against `haiec.declared.egress_allowlist` from span: this is not necessarily current approved policy. Read AR catalog contract/hard negatives; resolve qualified approved registries/policy where supported or downgrade semantics to explicitly **telemetry-asserted discrepancy**; gate unproven violation findings. Preserve valid AR detections and records. Include negative tests: no declaration, old/stale self-report, conflicting sources, an unrelated tenant scope.

**P0-D — untrusted evaluation/run IDs.** `detection-otlp-hook.ts` sets `evaluationId`/`runId` from `haiec.evaluation.id`/`haiec.run.id` span attributes; `persistDetectionFindings` stores them under org scope without showing an exact canonical run/eval verification in this write path. If not established, persist tenant-scoped telemetry finding **without** a fabricated evaluation/run association. Same-scope but different evaluation negative test.
