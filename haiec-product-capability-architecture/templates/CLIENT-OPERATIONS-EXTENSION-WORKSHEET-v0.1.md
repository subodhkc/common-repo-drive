# HAIEC — Optional Operations & Assurance Extension Plan
**Client worksheet / reusable generic template v0.1 | Draft, unfilled | No platform or live-integration claim**
Use this worksheet only to organize additional client operating work AFTER or alongside an eligible HAIEC objective. The HAIEC deterministic assurance engine itself does not require this document. You do not need to connect all sources or fill every part to receive a supported scoped evaluation.

## How to use (3 choices, 1 page by default)
**Choose ONE aim, not a 76-task checklist:**
- [ ] **A. Strengthen existing assurance** — validate an important UNKNOWN with another trusted source, authorized test or review
- [ ] **B. Expand operational monitoring** — connect more qualified events, source health, anomaly/drift and incident response
- [ ] **C. Activate target-side execution controls** — customer-specific gateway/PEP and kill/recover pilot, if feasible
- [ ] **D. Connect enterprise authority & change governance** — read actual IAM grants, tie changes to affected decisions
- [ ] **E. Extend executive/industry evidence** — selective framework, supplier, sector or reviewer delivery
- [ ] **F. Improve usage and reliability** — attribute provider spending or measure operational quality; hard budget caps only if separately established
- [ ] **G. No extension** — current HAIEC result already answers the customer objective, with known boundaries.

## Optional family-specific expansion cards
These are filters of the same client worksheet, not six different mandatory files.

### A. Extended Assurance & Independent Validation
Select only needed additional test/data: [ ] Provider-effective grant read [ ] reachability qualification [ ] prompt/tool/RAG abuse suite [ ] model quality & groundedness sample [ ] privacy/fairness/safety review for applicable population [ ] control replay/retest [ ] external evidence corroboration.
Output: source-qualified extra findings/tests with same engine evidence conventions. Additional evidence may preserve an UNKNOWN or reveal a new concern; no "buy stronger PASS".

### B. Connected Monitoring & Response Operations
Select: [ ] fresh producer/OTLP/gateway events [ ] observed action and baseline novelty [ ] config/permission/model drift [ ] explicit guardrail decision/coverage [ ] service/quality/cost signals [ ] alert to actual owner [ ] existing ticket/ACK/retest.
Output: in-scope signal health + qualified observations, separately verified response ownership. Do not promise invisible behavior is covered.

### C. Native Runtime Controls & Recovery
Select EXACT named reversible operation and client-owned PEP. Map actor, resource, action digest, policy version, human conditions, mandatory routes, background/retry/direct API bypass, durable claim, provider ACK/readback and recovery. Output only after real adapter installed and negative cases: actual scoped mediation evidence. If no PEP, output is a feasibility design ONLY.

### D. Enterprise Authority & Change
Select: [ ] actual cloud/provider IAM reader [ ] system-to-system delegated grant proof [ ] policy distribution/target digest [ ] CI/model/tool release impact [ ] human review/SoD [ ] approval stale/expired invalidation. Output: current effective authority and change linkage, never AI auto-approval.

### E. Portfolio & Industry Evidence
Select actual supported frameworks/contract profiles, system portfolio, accountable reviewers, sector impact, supplier provenance and report recipients. Output: source-bound evidence pack and review schedule, NOT ISO certification or compliance guarantee.

### F. Usage, Reliability & Spend
Select: [ ] provider usage basis [ ] actual bills vs provisional counters [ ] model/project attribution [ ] latency/errors [ ] token anomaly [ ] reservation/settlement feasibility. Output: accurate scoped visibility; preventative hard cap only after cross-worker reserve/settle acceptance and provider limits demonstrated.

## Short illustrative example, NOT a HAIEC evaluation or installed target
Goal: "Can the AI support agent change a customer refund limit?"
Existing: a HAIEC code-path evaluation identifies a candidate write operation and explicit uncertainty whether the external provider actually permits it.
Optional choice: A (one IAM read) to establish an effective grant. The engine already ran and stays truthful; the worksheet just recommends added independent evidence. If the customer additionally asks to block unauthorized changes in real time, C is a *separate* scoped customer-PEP engagement; an approved My Work decision alone is not a guard.
Monitoring afterwards: add source-qualified write-attempt traces only if desired/connected, map alert to a named owner; verify on-target effect separately. Keep time/scope/unknowns.
